# ADR 0001: メモ探索機能のデータモデルと検索方式

- 状態: Accepted
- 決定日: 2026-08-10
- 対象: 本文検索、カテゴリ分類、タグ絞り込み
- 詳細仕様: [`../features/memo-discovery.md`](../features/memo-discovery.md)

## Context

TagNoteはMarkdownメモの作成、一覧、詳細、編集、削除まで実装済みだが、保存件数が増えたときの探索手段がない。今後、本文キーワード検索、カテゴリ分類、複数タグによる絞り込みを追加する。

検索対象には日本語が含まれる。PostgreSQL組み込み全文検索はトークン化と辞書設定を前提とするため、初期版で日本語の「入力文字列を含む」という期待をそのまま満たす方式を選ぶ必要がある。また、カテゴリ／タグのIDを改ざんしても、他ユーザーの分類データをメモへ関連付けられないDB設計が必要である。

## Decision

### 1. 本文検索は `pg_trgm` とリテラル部分一致を採用する

- 正本である `memos.content` のMarkdownソースを `ILIKE` で部分一致検索する。
- 空白区切りの複数キーワードはANDで評価する。
- `%`、`_`、`\\` はエスケープし、ユーザーへ検索演算子として公開しない。
- `pg_trgm` のGINインデックスを `content` へ追加する。
- 検索結果は関連度順ではなく、既存と同じ更新日時順にする。

PostgreSQL組み込みの `tsvector` は、英語など辞書のある言語で語形正規化やランキングが必要になった時点で再評価する。PGroongaは日本語全文検索性能が実測目標を満たせない場合の候補とし、初期版では追加の検索構文や運用知識を導入しない。

### 2. カテゴリは1対多、タグは多対多にする

- `memos.category_id` はnullableとし、1メモに0または1カテゴリを割り当てる。
- `categories` 削除時は `category_id` だけをnullにし、メモを保持する。
- `tags` と `memos` は `memo_tags` で多対多にする。
- タグまたはメモ削除時は結合行だけをcascade削除する。
- カテゴリ色はDesign Systemの3種類に限定し、タグは色を持たない。

### 3. `owner_id` を関連テーブルへ持たせ、複合外部キーとRLSを併用する

- `categories`、`tags`、`memo_tags` はすべて `owner_id` を持つ。
- メモとカテゴリ、メモとタグの関連は `(owner_id, id)` の複合外部キーで所有者一致を保証する。
- すべての公開テーブルで `auth.uid() = owner_id` のRLSを有効化する。
- アプリケーションの認証チェックだけをセキュリティ境界にしない。

`memo_tags.owner_id` は正規化だけを考えると冗長だが、RLSを単純かつ検証可能にし、異なる所有者間の関連をDB制約で拒否できる利点を優先する。

### 4. 絞り込み状態はURLを正本とし、統合クエリをDB関数へ集約する

- `/memos` の `q`、`category`、`tags`、`page` が表示状態の正本となる。
- タグのAND条件、カテゴリ、本文、ページング、カード用集約は `security invoker` のDB関数で1回にまとめる。
- サーバーでURLを検証し、DB関数へ型付き引数だけを渡す。
- タグとカテゴリをメモごとに追加取得するN+1を許容しない。

## Consequences

### Positive

- 日本語を含む文字列を、辞書設定なしで予測可能に検索できる。
- 既存Markdown本文を変換／バックフィルせずに導入できる。
- カテゴリ／タグを削除してもメモを保持できる。
- 所有者の一致をRLSと外部キーの二重で保証できる。
- 検索とフィルタを共有、再読み込み、ブラウザ履歴で再現できる。
- 1 DB往復でカード表示データを取得し、N+1を避けられる。

### Negative

- 1〜2文字の検索や非常に一般的な語では、トライグラムインデックスの効果が弱い可能性がある。
- 検索は形態素解析、語形変化、表記ゆれ、関連度ランキングを提供しない。
- Markdownソース内のURLや記法文字列が一致する場合がある。
- `memo_tags.owner_id` と統合DB関数により、単純な多対多よりスキーマとテストが増える。
- DB関数の返却型変更時は、生成TypeScript型とアプリ側マッピングを同時に更新する必要がある。

## Rejected alternatives

### PostgreSQL組み込み全文検索だけを使う

語形正規化やランキングには有効だが、初期要件である日本語のリテラルな部分一致を、追加の日本語解析基盤なしで直感どおり提供しにくいため見送る。

### PGroongaを初期版から使う

多言語全文検索の有力候補だが、個人メモの初期規模に対して検索エンジン固有の構文、インデックス、運用判断が増える。`pg_trgm` が性能目標を満たさないことを計測してから再評価する。

### カテゴリを文字列、タグを配列として `memos` に保存する

実装は短くなるが、名称変更、重複防止、件数集約、所有者分離、参照整合性が弱くなるため採用しない。

### カテゴリとタグを同じテーブルにする

両者は多重度、削除動作、色、UI表現が異なる。単一テーブルは条件分岐と不正状態を増やすため分離する。

### Client Component内だけでフィルタ状態を管理する

URL共有、再読み込み、戻る／進む、Server Componentでの認証済み取得が不安定になるため採用しない。

## Review triggers

次のいずれかが起きた場合、このADRを再検討する。

- 代表データで本文検索のDB p95が500msを継続して超える。
- 表記ゆれ、自然言語ランキング、検索演算子がMust要件になる。
- 1メモへ複数カテゴリを付ける明確なプロダクト要件が承認される。
- チーム／共有メモにより、単一の `owner_id` では権限を表現できなくなる。
- 正確な全件数集計が検索性能の支配要因になる。
