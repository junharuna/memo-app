# メモ検索・カテゴリ・タグ機能 要件定義／設計／実装計画

- 状態: Implemented（代表データでの性能計測は継続課題）
- 対象リリース: 初期実装完了
- 最終更新: 2026-08-10
- 関連ADR: [`../adr/0001-memo-discovery-data-and-search.md`](../adr/0001-memo-discovery-data-and-search.md)
- UI基準: [`../design-system.md`](../design-system.md)

## 1. 目的と背景

現在のTagNoteでは、認証済みユーザーがメモを作成し、更新日時順の一覧、詳細、編集、削除を利用できる。一方、保存件数が増えたときに目的のメモへ到達する手段は更新日時と一覧走査に限られている。

本機能では、次の3つを一貫した「メモを見つける」体験として追加する。

1. Markdown本文に含まれるキーワードでメモを検索する。
2. 1つのカテゴリをメモへ割り当てて分類する。
3. 複数のタグをメモへ付け、タグで絞り込む。

検索・カテゴリ・タグは互いに独立した条件ではなく、`キーワード AND カテゴリ AND タグ` として組み合わせられることを前提とする。既存メモは移行後もカテゴリなし・タグなしで保持し、作成・表示・編集・削除の既存機能を壊さない。

### 1.1 現行調査の基準点

2026-08-10にSupabase MCPで接続先を再確認し、PostgreSQL 17.6へ本書どおりの組織化スキーマ、RLS、`pg_trgm`、検索／原子的保存関数を適用した。マイグレーションは `supabase/migrations/20260810190000_create_memo_organization.sql`、`20260810200000_add_memo_discovery_functions.sql`、`20260810203000_grant_memo_category_insert.sql` で管理し、生成型も同期している。既存メモはカテゴリなし・タグなしのまま保持した。

### 1.2 実装結果

- `/categories` と `/tags` で、所有者単位の作成、編集、件数表示、確認付き削除を実装した。
- メモ作成／編集はカテゴリ1件とタグ複数件をDB関数内で原子的に保存し、一覧カード、詳細、編集初期値へ反映する。
- `/memos` は本文キーワード、カテゴリ／未分類、複数タグAND、24件ページングをURLから復元し、条件の個別解除、全解除、件数、初期空とは異なる一致0件状態を表示する。
- ヘッダー検索、実カテゴリと件数を使うサイドバー、モバイルの確認ダイアログ式フィルタを実ルートへ接続した。
- Jest 129件、型チェック、Lint、プロダクションビルド、Supabase Security／Performance Advisors、認証済みPlaywrightの主要導線を確認した。Advisorsの未使用インデックス情報は導入直後かつ小規模データのため想定内であり、削除判断は代表データでの計測後に行う。
- 1ユーザー10,000件相当のp95計測は、接続先へ大量データを恒久投入しない検証環境を準備してから実施する。これは機能の利用可否を妨げない継続ハードニング項目とする。

## 2. ゴールと対象外

### 2.1 ゴール

- 日本語と英数字を含むMarkdown本文を、入力した文字列で検索できる。
- ユーザー自身のカテゴリとタグだけを作成、変更、削除、割り当てできる。
- 1メモにつきカテゴリは0または1件、タグは0件以上を割り当てられる。
- 複数条件を組み合わせた結果を、共有・再読み込み・戻る操作で再現できる。
- カテゴリまたはタグを削除しても、関連するメモ自体は削除されない。
- RLSとDB制約により、アプリケーション実装を迂回しても他ユーザーのデータへ到達できない。
- 既存の固定高メモカード、Markdownの安全性、レスポンシブ／アクセシビリティ基準を維持する。

### 2.2 今回の対象外

- タイトル検索、検索結果の関連度ランキング、曖昧検索、同義語、表記ゆれ吸収
- 検索演算子、フレーズ検索、除外検索、保存済み検索条件
- カテゴリ階層、複数カテゴリ、共有カテゴリ／共有タグ
- タグの色分け、タグ候補の自動生成、AIによる分類
- お気に入り、アーカイブ、ゴミ箱との連携
- 無限スクロール、ユーザーが選べる並び順
- MarkdownをHTML化した結果から検索専用テキストを抽出する処理

対象外の機能を将来追加するときも、本仕様のURL契約、所有者分離、既存データ互換性を維持する。

## 3. 用語と基本ルール

| 用語 | 定義 |
| --- | --- |
| 本文検索 | `memos.content` に保存された正規のMarkdownソースを対象とする部分一致検索 |
| カテゴリ | メモの主分類。1メモにつき0または1件 |
| タグ | メモの横断的な特徴。1メモにつき複数件 |
| 絞り込み | キーワード、カテゴリ、タグの条件をすべて満たすメモだけを表示すること |
| 未分類 | `category_id is null` のメモ |
| 所有者 | Supabase Authの `auth.uid()` と一致する `owner_id` のユーザー |

- 一覧の既定順は、現在と同じ `updated_at desc, id desc` とする。検索時も関連度順には変更しない。
- メモ編集フォームでタイトル、本文、カテゴリ、タグを保存したときは `memos.updated_at` を更新する。カテゴリ／タグ管理画面で分類名を変更または分類自体を削除しても、関連メモの更新日時は変更しない。
- 名前の先頭末尾の空白は保存前に除去する。同一ユーザー内では、大文字小文字を無視して同名のカテゴリ／タグを作れない。
- 既存ユーザーへ初期カテゴリや初期タグを自動作成しない。サンプル表示は実データへ置換する。

## 4. 機能要件

優先度は `Must`（初期リリース必須）と `Should`（初期リリース後の改善候補）で表す。

### 4.1 本文キーワード検索

| ID | 優先度 | 要件 |
| --- | --- | --- |
| SRCH-01 | Must | 認証済みユーザーはヘッダーまたはメモ一覧から本文キーワードを入力して検索できる。 |
| SRCH-02 | Must | 検索対象は現在のユーザーが所有する `memos.content` のみとする。タイトル、カテゴリ名、タグ名は検索対象に含めない。 |
| SRCH-03 | Must | 検索は日本語と英数字の部分一致とし、英字は大文字小文字を区別しない。 |
| SRCH-04 | Must | 空白で区切られた複数キーワードはAND条件とし、すべてを含むメモだけを返す。語順と出現位置は問わない。 |
| SRCH-05 | Must | `%`、`_`、`\\` はワイルドカードや制御文字ではなく、入力された文字として扱う。正規表現やSQL構文は受け付けない。 |
| SRCH-06 | Must | 入力値は前後空白を除去し、連続するUnicode空白を1つへ正規化する。空文字は検索条件なしとして扱う。 |
| SRCH-07 | Must | 検索文字列は100文字以下、分割後のキーワードは最大8個とする。超過時は入力欄に理由を表示し、検索を実行しない。 |
| SRCH-08 | Must | 検索条件はURLの `q` に保持し、再読み込み、戻る／進む、URL共有で同じ結果を再現できる。 |
| SRCH-09 | Must | 結果は1ページ24件とし、ページ移動後もすべての条件を維持する。 |
| SRCH-10 | Must | 一致しない場合は「条件に一致するメモがありません」と条件解除導線を表示し、メモが0件の初期空状態と区別する。 |
| SRCH-11 | Should | `⌘K`／`Ctrl+K` でヘッダー検索へフォーカスし、Escapeで入力のフォーカスを解除できる。 |

Markdownソースが正本であるため、見出し、リンクテキスト、コードブロック内の語句は検索できる。初期版ではリンクURLなどMarkdownソースにだけ存在する文字列も一致し得る。この挙動を避けるための検索用プレーンテキスト生成は、実利用上の問題を計測してから検討する。

### 4.2 カテゴリ

| ID | 優先度 | 要件 |
| --- | --- | --- |
| CAT-01 | Must | 認証済みユーザーは自分のカテゴリを作成、名称／分類色を変更、削除できる。 |
| CAT-02 | Must | カテゴリ名はtrim後1〜50文字とし、同一ユーザー内で大文字小文字を無視して一意にする。 |
| CAT-03 | Must | 分類色はDesign Systemの `blue`、`orange`、`violet` から選ぶ。色だけでカテゴリを識別させず、必ず名称を併記する。 |
| CAT-04 | Must | メモ作成／編集時に、自分のカテゴリを1件選択するか「カテゴリなし」を選べる。 |
| CAT-05 | Must | カテゴリで一覧を絞り込める。「未分類」も絞り込み条件として選べる。 |
| CAT-06 | Must | カテゴリ削除前に確認画面を表示し、対象メモ件数と「メモは削除されず未分類になる」ことを明記する。 |
| CAT-07 | Must | カテゴリ削除時は関連メモの `category_id` だけを `null` にし、メモとタグ割り当てを保持する。 |
| CAT-08 | Must | サイドバーには実データのカテゴリと件数を表示し、選択時は `/memos` の絞り込みへ遷移する。 |
| CAT-09 | Must | メモ詳細にはカテゴリ名を表示し、カテゴリ名から同じカテゴリの一覧へ移動できる。 |
| CAT-10 | Must | カテゴリが存在しない場合は作成導線を表示し、サンプルカテゴリを表示しない。 |

### 4.3 タグ

| ID | 優先度 | 要件 |
| --- | --- | --- |
| TAG-01 | Must | 認証済みユーザーは自分のタグを作成、名称変更、削除できる。 |
| TAG-02 | Must | 入力先頭の `#` は表示用記号として取り除き、タグ名をtrim後1〜30文字で保存する。同一ユーザー内で大文字小文字を無視して一意にする。`C#` のような途中／末尾の `#` は使用できる。 |
| TAG-03 | Must | メモ作成／編集時に、自分のタグを複数選択し、選択を解除できる。 |
| TAG-04 | Must | 保存済みタグはDesign Systemに従い `#タグ名` のニュートラルなチップとして表示する。タグごとの任意色は持たない。 |
| TAG-05 | Must | タグで一覧を絞り込める。複数タグを選んだ場合は、選択したすべてのタグを持つメモだけを返す。 |
| TAG-06 | Must | タグ削除前に確認画面を表示し、タグ割り当てだけが解除され、メモとカテゴリは残ることを明記する。 |
| TAG-07 | Must | メモ詳細にはすべてのタグを表示し、各タグからそのタグで絞り込んだ一覧へ移動できる。 |
| TAG-08 | Must | 一覧カードは最大2タグを表示し、残りは `+N` として固定高を維持する。本文は従来どおりMarkdownをレンダリングしない。 |
| TAG-09 | Must | タグが存在しない場合は作成導線を表示し、サンプルタグを表示しない。 |
| TAG-10 | Should | タグ選択欄は入力による候補絞り込みと、選択済みタグのキーボード削除に対応する。 |

### 4.4 条件の組み合わせ

| ID | 優先度 | 要件 |
| --- | --- | --- |
| FILT-01 | Must | 本文キーワード、カテゴリ、複数タグはANDで合成する。 |
| FILT-02 | Must | 適用中の条件を一覧上部へチップで表示し、個別解除と全解除を提供する。 |
| FILT-03 | Must | 条件変更時は `page=1` へ戻す。ページ移動時は条件を保持する。 |
| FILT-04 | Must | 存在しない、または他ユーザー所有のカテゴリ／タグIDは結果0件として扱い、所有者の存在を推測できるエラーを返さない。 |
| FILT-05 | Must | 不正なUUID、重複タグID、不正なページ値はサーバー側で正規化する。不正なURL値でDBエラーや500を発生させない。 |
| FILT-06 | Must | `/` の「最近のメモ」は従来どおり無条件の最新3件とし、検索／フィルタ結果は `/memos` に表示する。 |

## 5. 画面・操作設計

### 5.1 ルートとURL契約

| ルート | 役割 |
| --- | --- |
| `/memos?q=<text>&category=<uuid|none>&tags=<uuid,uuid>&page=<n>` | 統合された検索／絞り込み結果 |
| `/categories` | カテゴリの作成、名称／色変更、削除 |
| `/tags` | タグの作成、名称変更、削除 |
| `/memos/new` | カテゴリとタグを含むメモ作成 |
| `/memos/[id]/edit` | カテゴリとタグを含むメモ編集 |
| `/memos/[id]` | カテゴリとタグを含むメモ詳細 |

URLパラメータの正規形は次のとおりとする。

- `q`: 正規化後の検索文字列。空ならURLから除去する。
- `category`: カテゴリUUID、または未分類を示す予約値 `none`。条件なしなら除去する。
- `tags`: 重複除去し文字列順に並べたUUIDのカンマ区切り。0件なら除去する。
- `page`: 2以上の場合だけ付与し、既定の1は除去する。

URLを状態の信頼できる情報源とし、フィルタの主要状態をClient Componentだけに保持しない。サーバーで必ず再検証してからクエリへ渡す。

### 5.2 一覧

- ヘッダー検索の文言は対象を明確にするため「メモの本文を検索」とする。送信時に `/memos?q=...` へ遷移する。
- デスクトップは一覧見出しの下にカテゴリ／タグのフィルタを表示する。モバイルは40px以上の「絞り込み」ボタンからダイアログを開く。
- 適用中条件、結果件数、全解除を一覧の直前に表示する。
- メモカードは固定高を維持し、タイトル、プレーンテキスト抜粋、最大2タグ、カテゴリ、更新日時の順序を保つ。
- カード全体の詳細リンクと、タグ／カテゴリのフィルタリンクが競合する実装は避ける。カード内メタデータを操作可能にする場合は、カード全体を覆うリンクを廃止して見出しリンクへ変更する。

### 5.3 作成／編集

- タイトルと本文の保存フローへ、ラベル付きカテゴリ選択と複数タグ選択を追加する。
- カテゴリ／タグ候補は現在のユーザーのデータだけを名称順で表示する。
- 保存はメモ本体とタグ割り当てを1つのトランザクション相当で扱い、一部だけ保存された状態を残さない。
- カテゴリ／タグが未作成のときは管理画面への導線を表示する。初期版では編集フォーム内のインライン作成を必須としない。
- 保存失敗時は入力値と選択を保持し、どの処理に失敗したかをフォーム近傍で通知する。

### 5.4 管理画面

- `/categories` と `/tags` は共通シェル内の認証必須ページとする。
- 各行に名称、関連メモ件数、編集、削除を表示する。削除は確認ダイアログを必須とする。
- 作成と名称重複などの検証エラーは対象入力へ関連付ける。成功は共通トーストで通知する。
- 件数取得は一覧ごとの個別問い合わせを行わず、集約クエリ1回で取得する。

### 5.5 状態とアクセシビリティ

- Loading、データ0件、条件一致0件、取得失敗、更新失敗を別の状態として設計する。
- 検索結果更新後は結果件数を `aria-live="polite"` で通知する。入力のたびに通信せず、フォーム送信または明示的な条件適用で更新する。
- フィルタ、タグ選択、確認ダイアログはキーボードだけで完結でき、フォーカスを可視化する。
- 色だけでカテゴリ選択を表現せず、名称、選択状態、必要に応じてアイコンを併記する。
- 390pxと1440px、ライト／ダーク、200%拡大、長い日本語名、キーボードフォーカスを確認する。
- モーションを加える場合は `prefers-reduced-motion` で無効化できるようにする。

## 6. データ設計

### 6.1 ER構造

```mermaid
erDiagram
  AUTH_USERS ||--o{ MEMOS : owns
  AUTH_USERS ||--o{ CATEGORIES : owns
  AUTH_USERS ||--o{ TAGS : owns
  CATEGORIES o|--o{ MEMOS : classifies
  MEMOS ||--o{ MEMO_TAGS : has
  TAGS ||--o{ MEMO_TAGS : assigned

  MEMOS {
    uuid id PK
    uuid owner_id FK
    uuid category_id FK nullable
    text title
    text content
    timestamptz created_at
    timestamptz updated_at
  }
  CATEGORIES {
    uuid id PK
    uuid owner_id FK
    text name
    text color_key
    timestamptz created_at
    timestamptz updated_at
  }
  TAGS {
    uuid id PK
    uuid owner_id FK
    text name
    timestamptz created_at
    timestamptz updated_at
  }
  MEMO_TAGS {
    uuid owner_id FK
    uuid memo_id FK
    uuid tag_id FK
    timestamptz created_at
  }
```

### 6.2 テーブルと制約

#### `public.categories`

| 列 | 型 | 制約／用途 |
| --- | --- | --- |
| `id` | `uuid` | PK、`gen_random_uuid()` |
| `owner_id` | `uuid` | NOT NULL、`auth.users(id) on delete cascade` |
| `name` | `text` | NOT NULL、保存値がtrim済みの1〜50文字 |
| `color_key` | `text` | NOT NULL、`blue / orange / violet` のCHECK |
| `created_at` | `timestamptz` | NOT NULL、`now()` |
| `updated_at` | `timestamptz` | NOT NULL、`now()`、更新トリガー |

- `(owner_id, id)` に一意制約を置き、所有者を含む複合外部キーから参照できるようにする。
- `name = btrim(name)` と文字数のCHECK制約で、APIを直接利用しても未正規化値を保存できないようにする。
- `(owner_id, lower(btrim(name)))` の一意インデックスでユーザー内の重複名を防ぐ。
- `(owner_id, lower(name))` を管理画面の名称順取得へ利用する。

#### `public.tags`

| 列 | 型 | 制約／用途 |
| --- | --- | --- |
| `id` | `uuid` | PK、`gen_random_uuid()` |
| `owner_id` | `uuid` | NOT NULL、`auth.users(id) on delete cascade` |
| `name` | `text` | NOT NULL、保存値がtrim済みの1〜30文字、先頭は `#` 以外 |
| `created_at` | `timestamptz` | NOT NULL、`now()` |
| `updated_at` | `timestamptz` | NOT NULL、`now()`、更新トリガー |

- カテゴリと同じく `(owner_id, id)` の一意制約と、正規化名のユーザー単位一意インデックスを持つ。
- `name = btrim(name)`、文字数、`left(name, 1) <> '#'` のCHECK制約を持つ。表示時に先頭の `#` を付与し、`C#` のように先頭以外の `#` は許可する。

#### `public.memos` の変更

- `category_id uuid null` を追加する。
- `(owner_id, id)` に一意制約を追加する。
- `(owner_id, category_id, updated_at desc)` に一覧用インデックスを追加する。
- `(owner_id, category_id)` から `categories(owner_id, id)` への複合外部キーを設定し、削除時は `category_id` だけを `null` にする。これにより他ユーザーのカテゴリを割り当てられない。
- authenticatedロールのUPDATE列権限へ `category_id` を追加する。`owner_id` の更新権限は与えない。

#### `public.memo_tags`

| 列 | 型 | 制約／用途 |
| --- | --- | --- |
| `owner_id` | `uuid` | NOT NULL、RLSと複合外部キーに使用 |
| `memo_id` | `uuid` | NOT NULL |
| `tag_id` | `uuid` | NOT NULL |
| `created_at` | `timestamptz` | NOT NULL、`now()` |

- PKは `(owner_id, memo_id, tag_id)` とし、同じタグの重複割り当てを防ぐ。
- `(owner_id, memo_id)` を `memos(owner_id, id)` へ、`(owner_id, tag_id)` を `tags(owner_id, id)` へ、いずれも `on delete cascade` で参照する。
- タグ削除時は結合行だけが削除され、メモは残る。メモ削除時はタグ自体を残して結合行だけを削除する。
- タグ絞り込み用に `(owner_id, tag_id, memo_id)` のインデックスを追加する。

### 6.3 RLSと権限

`categories`、`tags`、`memo_tags` のすべてでRLSを有効化し、各操作を `(select auth.uid()) = owner_id` に限定する。

| テーブル | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| `categories` | 自分のみ | 自分のみ | 自分の `name,color_key` のみ | 自分のみ |
| `tags` | 自分のみ | 自分のみ | 自分の `name` のみ | 自分のみ |
| `memo_tags` | 自分のみ | 自分のみ | 不許可 | 自分のみ |
| `memos` | 既存方針 | 既存方針 | `title,content,category_id` | 既存方針 |

- `anon` へ権限を与えない。
- サーバー処理は `getClaims()` で認証を確認し、Service Roleキーを使用しない。
- 複合外部キーとRLSの両方で所有者の一致を保証する。UIやServer Actionだけをセキュリティ境界にしない。
- DB関数は原則 `security invoker`、`set search_path = ''` とし、公開実行権限を剥奪して必要なauthenticatedロールへだけ付与する。

## 7. 検索・取得設計

### 7.1 検索方式

初期版はPostgreSQLの `pg_trgm` 拡張と、`content ILIKE '%keyword%'` に対応するGINインデックスを使う。

```sql
create extension if not exists pg_trgm with schema extensions;

create index memos_content_trgm_idx
  on public.memos
  using gin (content extensions.gin_trgm_ops);
```

採用理由は次のとおり。

- 日本語の単語分割器へ依存せず、ユーザーが入力した文字列をそのまま部分一致できる。
- Markdownソースを正本のまま検索でき、検索専用列の同期処理が不要である。
- PostgreSQLの標準拡張であり、接続中のSupabaseプロジェクトで利用可能だと確認済みである。
- `LIKE`／`ILIKE` のインデックス検索を利用できる。

1〜2文字の短い検索語はトライグラムインデックスの効果が限定され得るが、日本語では2文字語も一般的なため機能上は禁止しない。ユーザーごとの所有者条件、入力上限、ページングで負荷を限定し、実データ相当の計測結果が目標を満たさない場合はPGroongaまたは検索専用列を再評価する。

### 7.2 統合クエリ

タグのAND条件、カテゴリ、本文検索、ページング、関連メタデータ集約を1回で行うため、公開契約を1つのDB関数へ集約する。名称例は `public.search_memos` とする。

```text
search_memos(
  search_terms text[] default '{}',
  category_filter uuid default null,
  include_uncategorized boolean default false,
  tag_filters uuid[] default '{}',
  result_limit integer default 24,
  result_offset integer default 0
)
```

返却値にはカード表示に必要なメモ列、カテゴリ、タグ配列、全件数を含める。タグとカテゴリをメモごとに追加取得せず、SQL内で集約してN+1を避ける。

関数内では次を必須とする。

1. `auth.uid()` がnullなら0件を返す。
2. `memos.owner_id = auth.uid()` を明示し、RLSも適用する。
3. 各検索語の `%`、`_`、`\\` をLIKEリテラルとしてエスケープし、すべての語を含むか検査する。
4. タグIDは重複除去済み配列として受け、該当メモの一致タグ数が配列長と等しいことを検査する。
5. カテゴリIDが指定されたときは一致を、未分類指定時は `category_id is null` を検査する。
6. `result_limit` は1〜24、`result_offset` は非負へ制限する。
7. `updated_at desc, id desc` で安定して並べる。

ページ側はURLを `parseMemoFilters` のような純粋関数で検証し、DB関数へ型付きの値だけを渡す。ユーザー入力からPostgRESTの `.or()` 文字列やSQL断片を組み立てない。

### 7.3 書き込み設計

- カテゴリ／タグのCRUDはServer Action経由とし、認証、入力検証、DBエラーのユーザー向け変換を共通化する。
- メモ作成は `create_memo_with_metadata`、メモ編集は `update_memo_with_metadata` のような `security invoker` DB関数へ集約し、メモ本体の書き込みとタグ差し替えを同一トランザクションで行う。`owner_id` は引数で受け取らず `auth.uid()` から確定する。
- メモ編集関数はタイトル、本文、カテゴリ、タグをまとめて保存し、成功時に `memos.updated_at` を更新する。一部だけ更新された状態を作らない。
- メモID、カテゴリID、タグIDのすべてで所有者を再確認する。他ユーザーID指定時はnot found相当とし、存在有無を漏らさない。
- 一意制約違反は「同じ名前がすでにあります」、参照先削除との競合は「一覧を更新してもう一度お試しください」と明示する。
- 成功時は関連する `/`、`/memos`、詳細、カテゴリ／タグ管理画面を `revalidatePath` する。

## 8. 非機能要件

### 8.1 セキュリティとプライバシー

- 検索語や本文をアプリケーションログ、分析イベント、エラーメッセージへ記録しない。記録する場合は条件種別、件数、処理時間だけとする。
- 入力の長さ、配列数、UUID形式をアプリとDB境界の両方で制限する。
- Reactの通常エスケープを維持し、カテゴリ名／タグ名をHTMLとして解釈しない。
- 他ユーザーのカテゴリ／タグIDを渡しても、データ、名称、件数、存在を取得できないことをRLSテストで保証する。

### 8.2 性能

- メモ一覧取得はメモ、カテゴリ、タグを含め原則1 DB往復とし、N+1を禁止する。
- 1ユーザー10,000メモ、平均本文5KB、1メモ平均3タグの代表データで、DB検索のp95 500ms以下を初期目標とする。
- `EXPLAIN (ANALYZE, BUFFERS)` で本文検索、カテゴリ、1タグ、3タグ、全条件のクエリ計画を確認する。
- 検索結果は24件単位で取得し、画面表示のために本文全文をクライアントへ送らない。カード用抜粋生成に必要な上限付きデータを返す方法も計測して判断する。
- 正確な全件数が性能目標を阻害する場合は、ページ件数+1件の取得による前後ナビゲーションへ変更し、仕様書を更新する。

### 8.3 信頼性と保守性

- 通信／DB失敗時は結果0件に見せず、再試行可能なエラー状態を表示する。
- DBマイグレーションは既存メモへデフォルト分類を強制せず、null許容の加算変更とする。
- 検索条件の型、DB関数の返却型、UIモデルを別々に重複定義せず、生成DB型とドメイン変換を信頼できる情報源にする。
- 新しい依存パッケージは追加せず、Supabase、React、既存UI基盤で実装する。必要性が生じた場合はライセンス、容量、保守状況を先に記録する。

## 9. TDD・検証計画

各実装単位はRed → Green → Refactorで進める。リモートSupabaseへ依存するテストをJestの通常テストへ混ぜず、アプリ層はSupabaseをモックする。

### 9.1 ユニット／コンポーネントテスト

- URL解析: 空値、Unicode空白、100文字境界、9キーワード、不正UUID、重複タグ、`none`、不正ページ
- 検索: 日本語、英字の大小、複数語AND、`%`／`_`／`\\`、一致0件、DB失敗
- カテゴリ: 作成、重複、長さ、色、割り当て解除、削除確認、削除失敗
- タグ: 作成、先頭 `#` の正規化、`C#` の許可、重複、複数選択、全タグAND、差し替え失敗
- 一覧: 条件表示、個別／全解除、ページリンクへの条件引き継ぎ、カードの最大2タグと `+N`
- 権限結果: unauthenticated、not found、query errorを正常な空状態と区別する
- 操作性: ラベル、アクセシブル名、ダイアログのフォーカス、エラーの関連付け、`aria-live`

### 9.2 DB統合テスト

Supabaseの開発ブランチまたはローカルDBで、最低限次を自動検証する。

1. 全新規テーブルでRLSが有効である。
2. ユーザーAはユーザーBのカテゴリ、タグ、結合行をSELECT／INSERT／UPDATE／DELETEできない。
3. ユーザーBのカテゴリ／タグをユーザーAのメモへ割り当てる複合外部キー違反が発生する。
4. カテゴリ削除後もメモが残り `category_id` だけがnullになる。
5. タグ削除後もメモが残り、対象の結合行だけが消える。
6. メモ削除後もタグは残り、対象の結合行だけが消える。
7. 同一ユーザー内の大文字小文字違い／前後空白違いの重複名を拒否する。
8. 本文検索、未分類、複数タグAND、全条件の組み合わせが期待したIDだけを返す。
9. 他ユーザーIDをフィルタへ指定しても0件となり、情報を返さない。
10. `EXPLAIN` で代表的な本文検索がトライグラムインデックスを利用できる。

マイグレーション適用後はSupabaseのSecurity AdvisorとPerformance Advisorを確認し、TypeScriptのDB型を再生成する。

### 9.3 Playwright MCPによる実ブラウザ検証

AGENTS.mdの認証済みブラウザ手順に従い、保持済みセッションを再利用する。各機能段階で次を確認する。

- 日本語本文を含むメモを検索し、一致／不一致と複数語ANDを確認する。
- カテゴリを作成してメモへ割り当て、一覧絞り込み、詳細表示、名称変更を確認する。
- カテゴリを削除してもメモが残り、未分類になることを確認する。
- 複数タグを作成／割り当てし、1タグと複数タグANDの結果を確認する。
- タグを削除してもメモとカテゴリが残ることを確認する。
- 条件を組み合わせ、再読み込み、戻る／進む、ページ移動で状態が維持されることを確認する。
- 390px／1440px、ライト／ダーク、キーボードフォーカス、長い名称、空／エラー状態を確認する。
- 検証データを作る前に用途を明確にし、完了後の削除が必要ならユーザーの許可範囲内で行う。

## 11. リリースとロールバック

- DB変更は既存アプリが無視できる加算変更として先に適用し、その後アプリをリリースする。
- 組織化スキーマと検索は別マイグレーションにし、失敗箇所を限定する。
- 既存メモの `category_id` はnullのままとし、バックフィルやデータ書き換えを行わない。
- アプリのロールバック時は追加テーブル／列を直ちに削除しない。旧アプリが利用しない状態で保持し、データ損失を避ける。
- インデックス作成時間が問題になるデータ量へ成長した場合は、低トラフィック時間帯またはconcurrent作成の手順を別途策定する。
- 本番適用前後でメモ件数、RLS有効状態、主要クエリ、Advisorsを比較する。

## 12. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 短い日本語検索でGINの効果が弱い | 検索遅延 | 所有者条件、上限、ページング、実測。未達ならPGroonga／検索列をADR更新のうえ再評価 |
| タグ集約によるN+1または重複行 | 遅延、カード重複 | 統合DB関数で集約し、件数／IDのテストを追加 |
| URLへ不正IDが渡る | 500、情報漏えい | サーバーで型検証し、他所有者IDは0件扱い、RLSを併用 |
| カテゴリ／タグ削除がメモ削除へ波及 | データ損失 | FKの削除動作を明示し、DB統合テストと確認文言で保証 |
| メモ保存とタグ保存の一部失敗 | 不整合 | DB関数内で原子的に差し替え、失敗時は入力を保持 |
| 固定高カードへメタ情報が増える | UI崩れ | タグ最大2件+N、カテゴリ1件、長文clampを390px／1440pxで確認 |
| 検索語がログへ残る | プライバシー侵害 | 生の検索語を記録せず、件数と時間だけを計測 |
